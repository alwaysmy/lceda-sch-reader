# 缺失分析与改进建议

> 2026-08-31 对 lceda_sch_reader 现状的评估结论（非代码改动，仅记录与建议）。
> 背景：项目目录名为 `sch_review_tool`，但当前落地的 `lceda_reader.py`
> 本质是**只读解析器**，「审查」这件事本身尚未开始。本文按优先级分层记录
> 缺失项，供后续 roadmap 参考。

## 一、总体结论

格式读取层已经相当扎实——三种后端（LcedaDB/EproDB/Epro2DB）+ 新版加密分支
自动解密 + CBB 展开 + 连通域精确方案，是整个项目最硬的部分，完成度高。
真正的缺口在**上层规则引擎与工程化**，而不是继续往读取层加功能。

## 二、缺失清单

### A. 审查工具本体缺失（最根本，优先最高）

1. **没有审查规则引擎 + 报告生成器**。21 个命令全部是「查询原语」，
   设计启发文档中的 `{id, scope, check(ctx)→findings, severity, evidence}`
   规则注册机制、finding 证据链、置信度分级（原则 1）都只停留在文档，
   一行代码未落地。
2. **没有 `review_rules.json` 配置层**（工具配置 vs 工程配置分层只写了文档）。
3. **「可直接落地的审查点清单」几乎全待写**：位号唯一性/连续性、
   标题栏完整性、网络命名规范、图纸质量（文本重叠/出图区）、悬空未命名
   网络残端、NC 引脚确认清单。目前只有 `polar`/`pcbsch`/`link-check`
   三个命令长成了「审查结论」雏形，且彼此孤立、无统一框架。

### B. 架构 / 工程化缺失

1. **单文件 4500+ 行技术债**：`cmd_render` 约 600 行闭包嵌套；`cmd_*`
   内部直接 `sys.exit()`，库化复用时劫持进程。设计启发文档 Phase 1/2
   （拆包 `backends.py`/`model.py`/`render.py`/`cli.py`、sys.exit 改
   raise ToolError）已规划但未实施。
2. **无正式测试套件**：`smoke2.py`/`verify_all_formats.py`/
   `cross_backend_contract.py` 是脚本而非测试框架，无 pytest、无 CI；
   回归靠 AGENTS.md 里「人肉逐字节对比 + 手工跑三件套」的纪律，不可自动化、
   换人/换机即不可复现。
3. **「仅依赖标准库」与实现不符**：README 第七节、SKILL.md 均称「仅依赖
   Python 标准库」，但 `_decrypt_new_eprj2()` 实际依赖第三方
   `cryptography`（`AESGCM`），`probes/crop_agnd.py`、`probes/cmp_bl.py`
   还依赖 `Pillow`（PIL）。虽 `cryptography` 为懒加载、仅新版加密格式需要，
   但新版 `.eprj2` 恰是当前最常见场景——等于「主场景需额外依赖」，文档措辞
   失真，应同步修正（或明确标注「核心只读路径纯标准库，解密/PIL 探针需额外
   依赖」）。
4. **机器可读输出无 schema 版本**：`--json` 无 version 字段、无 schema
   文档，字段变更会让下游脚本/agent 静默拿到错数据。
5. **文档滞后与状态漂移，缺单一权威限制清单**：README 命令清单缺
   `texts`/`pcbsch`/`polar`/`docs`/`render` 五个命令（SKILL.md 与 CLI 均有，
   README 落后）；已知限制散落多份「时间点快照」文档且状态矛盾——例：
   `设计审查与修复-2026-08-21.md` 仍列「网络名含逗号破坏 dom join」为遗留，
   而 `开发文档.md` §4.5 已记「NET_SEP(\u241f) 规避逗号歧义」（已修）。缺一份
   随代码更新的「当前已知限制/状态」权威表。

### C. 解析能力缺失（部分 TODO 已有，此处补充判断）

1. **BUS / BUSENTRY**：文档定性为「等含总线样例」。但从审查工具角度是
   **必修项而非可选项**——MCU 工程总线极常见，缺失导致含总线工程漏网络、
   断链，审查结论直接不可信。建议主动找样例补齐。
2. **V3 符号图形**：`.epro2`/新 `.eprj2` 渲染退化为占位框，渲染作为
   「复核证据」的能力（原则 3）在 V3 工程上失效。
3. **交付物一致性 / 过期审计（原「SCH↔PCB 逐 pin 网络对比」修正定位）**：
   `pcbsch` 只到器件级「反标/漏布局」。澄清：「SCH netlist == PCB netlist」
   在立创EDA 集成工作流里由原生同步机制保证（PCB net 即从原理图派生，更新
   PCB 时有变更比对），既非 ERC 也非 DRC，但作为「净比对」能力大多冗余，
   **不算审查工具的核心价值**。真正非冗余的是**交付物漂移/过期审计**：工程师
   改完原理图未重新同步 PCB 就交付/归档，文件内无「已同步」标记，审查者需
   独立证明「这份 PCB 对得上这份 SCH」。实现靠 `Unique ID` 对齐 SCH pin 与
   PCB pad 后 diff 两侧 net——**吃的是 Unique ID 对齐，不是 PAD 几何**；PAD
   几何仅用于把焊盘映射到引脚。这条应落在规则引擎里，作为一条「一致性规则」，
   输出「疑似未同步/过期」finding。
4. **版本 diff**：跨格式 `Unique ID` 稳定性已实证，但 `diff` 命令未封装；
   低成本、高收益的顺手项。
5. **BOM 公式属性真实性**：`resolve()` 链已实现，但 BOM 未接公式解析，
   拿到的是「字面值」而非「解析后真值」，含公式参数的工程会漏。
6. **符号/封装与 datasheet 一致性核对（含设计规范）**：目前无能力核对
   器件符号的引脚名/号/功能是否与 datasheet 实际定义一致（如 pin1 被标成
   GND 而手册是 VCC、三极管引脚对调），也无能力核对 PCB 封装焊盘映射/尺寸
   是否符合 datasheet 推荐封装、并进一步符合 IPC-7351 等设计规范（焊盘 1
   标识、散热焊盘连接、引脚间距、丝印极性标记）。这是 ERC/DRC 都覆盖不到的
   审查层能力——ERC 不管引脚定义对不对，DRC 不管封装语义对不对。前提缺口：
   ① 封装 PAD 几何的字段定义已在字段字典（官方 §1.5），但工具尚未消费 PAD
   几何（引脚号/坐标/尺寸）建立 footprint 逐 pin 映射；② datasheet 结构化
   引脚表需从 PDF 提取（当前 `datasheets` 只给 URL，不解析内容）；③ 设计
   规范规则库（IPC-7351 等）需外置并标注依据级别。属「审查规则 + 外部证据
   源」的组合，不只是解析能力。
7. **字段字典 §4「待验证/未消费」项（细粒度）**：`INSTANCE/*.eins` 的
   OVERRIDE 覆盖路径语法、`PIN a[3]` 电气特性 vs ATTR "Pin Type" 一致性
   验证、`RECT` 的 rot 绕点1 对渲染的影响（当前 rotate 为近似）、
   `OBJ/blob` 资源 / FONT 路径缓存 / 3D SHELL 体系——均未消费。

### D. 鲁棒性 / 边界 / 长期维护缺失

1. **格式演进脆弱**：立创EDA 已历经 V2 SQLite → V3 ZIP → 加密分支多版，
   未来大概率继续变。当前靠 `detect_backend` 内容嗅探 + 明确报错兜底，
   无「格式版本显式探测 → 未知版本硬报错」机制，新格式可能静默返回空结果
   （历史上真实发生过的静默空结果事故）。
2. **性能无缓存**：`Epro2DB` 每次运行全量扫 `.epru` 建索引（数秒级），
   `_cbb_sig` 每次重建；100MB+ 大工程未测。交互式/web 场景缺磁盘索引缓存。
3. **写回能力为零**：工具全只读。openlceda 或「审查后落修复建议」需要写回，
   而增量 ticket 合并、分支版本化是未验证的高风险区——openlceda 愿景据此还很远。
4. **多工程命令只在旧格式验证**：`netfind`/`trace`/`link-check`/`find`/
   `search` 的多工程模式在 `.epro`/`.epro2` 上未系统验证，而连接器跨板
   核对恰恰是最依赖多工程的审查场景。
5. **使用边界/免责声明与 LICENSE 缺失**：解密能力本质是绕过立创EDA 的文件
   保护机制，仓库无任何「仅限读取用户本人拥有/授权工程」的使用边界声明，
   且根目录无 LICENSE 文件（二者一体，开源/复用时需明确）。
6. **`export_newfmt.py` 游离于仓库根而非 `probes/`**：与 AGENTS.md
   「探针/脚本放 probes/」纪律不一致（虽为正式备选工具、SKILL 有文档，
   位置略显游离）。小项。

## 三、优先级建议（roadmap）

1. 审查规则引擎 + 报告生成器（项目真正目标，其余是底座；首批高价值规则
   应包括交付物一致性审计、符号/封装与 datasheet 核对，以及 A.3 所列
   可直接落地的审查点）。
2. 拆包 + 去 `sys.exit` + 补 schema version（为规则引擎与 web 交互铺路，
   同时还技术债）。
3. BUS 支持 + 交付物一致性/过期审计（补齐两个会让审查结论「失真」的能力；
   「PCB 逐 pin 对比」已重新定位为一致性审计，见 C.3）。
4. 版本 diff + BOM 公式接入（低成本高价值顺手项）。
5. 补测试套件、性能缓存、修正「仅标准库」表述、补 LICENSE/使用边界声明，
   并建立单一权威的已知限制清单。
