# 网络别名未合并导致连通性漏查

- 日期：2026-10-28
- 类型：缺陷分析 + **修复记录（已实现并回归）**
- 涉及命令：`nets` / `netlist` / `netfind` / `pinmap` / `search`
- 涉及代码：`lceda_reader.py` 端口命名段、`resolve_nets_by_domain`、
  别名闭包助手（`build_alias_groups` / `pick_primary_name`）与聚合命令

> 通用问题：**同一物理连通域上存在多个网络名时，工具只保留一个名字**，
> 导致 `netfind A` 与 `netfind B` 返回互不包含的结果，使用者据此会漏掉整段电路。
> 本文 §2 只给一个具体工程作示例，其余描述与工程无关。

---

## 1. 缺陷描述

立创EDA 中同一根导线可以有多个命名来源：

1. 导线自身的 `NET` / `Global Net Name` 属性；
2. 压在这根导线上的 NetPort / NetFlag 符号的 `Name` 属性；
3. 跨页时不同页的端口分别命名（同一物理网络在不同页有不同名字）。

工具目前的命名策略是"**只在导线未命名时采用端口名**"：

- 导线已有 `NET` → 端口名被丢弃，网络模型里只剩导线名；
- 别名集合只在**同页**内做闭包（`resolved_nets`），**不跨页传递**。

结果：物理上是一根线，查询上被拆成两组互不包含的成员。

### 1.1 与"是否已有一部分别名功能"的区分（重要）

工具**已经有**同页别名闭包：`pinmap` 默认输出的 `resolved_nets` 字段，
用于保留"同页显式短接 / 同名网络"形成的别名集合（2026-10-01 落地，
见 README §一 与 `docs/开发文档.md` §4 第 5 条"同页别名闭包"）。

所以本缺陷**不是"没有别名功能"**，而是两个缺口：

| # | 缺口 | 位置 | 现状（2026-10-28） |
|---|---|---|---|
| A | 端口名压在**已命名导线**上时不进入网络模型 | 端口命名传播分支（约 3811 / 3848） | **已修复**：以 `NET_SEP` 多值并入 `net_of`/`sheet["nets"]`/`endp` |
| B | 别名集合**不跨页**闭包，跨页只按"同名"桥接点集 | 聚合命令（`nets`/`netlist`/`netfind`） | **已修复**：域建成后用 `build_alias_groups` 做全局并查集 |

实测（示例工程）：同一根线上 `PC4` 的 `resolved_nets` 已能给出两个名字
（同页闭包生效），但另一页只有其中一个名字，`netfind` 仍只返回单页成员。

## 2. 现象与示例（仅此处涉及具体工程）

示例工程：`ProPrj_MMC-110-MultiFields.epro2`（只作复现用，不是问题范围）。

| 查询 | 返回 |
|---|---|
| `netfind USART2_TX` | 6 个连接点（单页：MCU 引脚、排针、短接符、端口） |
| `netfind ID_OUT` | 9 个连接点（三页，含二极管阴极、排针、ESD、串联电阻） |

两者是同一物理网络的两种叫法。同类现象在该工程还有一对：
`USART1_TX` 4 个点 vs `ID_OUT_MC` 7 个点——说明不是孤例。

影响面（判据：端口 `Name` 未出现在该页最终网络名集合）：该工程 391 个
NetPort/NetFlag 实例中，**2 个**端口名未进入本页网络模型——即缺口 A
在真实工程里是**窄口径但确实发生**的，不应被"别名功能已存在"掩盖。

## 3. 源码定位（更正版）

端口命名段的实际逻辑：

```python
for cid in port_cids:
    nm = net_of.get(cid) or attrs_of.get(cid, {}).get("Name")   # 3785（正常取到 Name）
    if nm:
        port_nets[cid] = nm

for (des, cid), plist in comp_pins.items():
    ...
    for wid2 in pt_wires.get(pt, ()):
        cur = net_of.get(wid2)          # 3811
        if cur:                         # 导线已命名 -> 并别名（原为 continue）
            toks = net_tokens(cur)
            if nm in toks:
                continue
            merged = NET_SEP.join(sorted(set(toks) | set([nm])))
            net_of[wid2] = merged
            ...                         # 同步 sheet["nets"] 条目与 endp
            continue
        net_of[wid2] = nm               # 未命名 -> 直接命名（原行为）
        ...

# 末尾 fallback：端点已被覆盖时仍跳过（别名已在上面并入）
if pt in have or endp.get(pt) is not None:   # 3848
    continue
```

**结论（含更正）**：

- **3785 不是缺陷点**。NetPort/NetFlag 实例自身通常**没有** `NET` 属性，
  因此 `net_of.get(cid)` 为 `None`，`Name` 会被正常取到。
  在这一行做"多值合并"对"导线已命名"场景**无效**。
- **3811 是主因（已修复）**：导线已有 `NET` 时直接 `continue`，端口名不写入
  `net_of` / `sheet["nets"]` / `endp`，后续连通域自然看不到。
- **3848 是同一缺陷的第二条路径**：端点已被覆盖时不再补别名。

## 4. 实现（2026-10-28 已落地）

### P0-1 别名入域（改 3811 / 3848，不是 3785）——已完成

对**已命名**导线也追加端口名：以 `NET_SEP` 多值写入
`net_of` / `sheet["nets"]` / `endp`，去重且幂等；`net` 字段语义不变。

### P0-2 全局别名闭包——已完成

新增 `build_alias_groups()`：把所有页域内的名字做一次并查集（名字共现即同组），
同名跨页自然连通（A≡B、B≡C → 同一组）。保持既有约束：NC/DNP 不产生桥、
不跨普通有源器件。`resolve_nets_by_domain` 收集域内名字时按 token 拆分，
因此多值 `endp` 不会把 `A␟B` 当成一个名字。

### P0-3 别名显示与输出标注——已完成（与 P0-1/P0-2 同批）

| 输出 | 实际行为 |
|---|---|
| `nets` / `netlist` 文本 | 并列全部名字 `A, B, C`；同一物理网络只占**一行** |
| `netfind` 文本 | 标题 `== 网络 A, B, C (n 个连接点) ==` |
| `pinmap` 文本 | 引脚行并列全部名字；`--no-domain` 不输出 |
| JSON（上述命令） | **仅当存在别名时**新增 `aliases`（全组名字）；无别名时不加字段 |
| `pinmap --json` | 保留 `resolved_nets`；有别名时追加同值的 `aliases` |
| `--json-report` | `completeness_scope` 含 `alias_closure`，顶层输出 `alias_groups` |
| 主名 | `pick_primary_name`：非引脚自动名优先 → 引脚数多者 → 字典序；只影响 JSON 的 `net` 与排序，文本始终并列全名 |

## 7. 因果边界（写结论时必须遵守）

网络表只能证明"**同一网络上有多个潜在驱动源**"，不能证明：

- 某一时刻两个驱动是否同时有效（取决于使能时序/固件状态）；
- 电气结果谁赢（取决于驱动能力、串联器件压降）；
- 该网络就是某次通信失败的**原因**。

因此文档与汇报中不得把"同一网络上有两个输出"直接写成"功能必然失效"。
本次示例工程的实际故障，后续实测另有结论（与本缺陷无因果关系），
本缺陷的成立与否不依赖该故障。

## 8. 附：`netfind` 的适用边界（不是缺陷）

排查时容易把"netfind 看不到另一端"误判为工具不可靠。典型情形：

- `netfind <MCU 引脚>` 只返回 `MCU 引脚 + 串联电阻一端`（2 个点），
  不含串阻另一端所接的 LED/GND；
- 这不是漏查：`netfind` 的语义是"**同一网络**"，串阻两侧本来就是两个网络。
  要看链路请用 `pinmap`（逐脚递归）或 `trace`（多跳），
  或在 `polar` 里看二极管/LED 两端与"同线"对象；
- 只有"**同一网络多个名字**"才是缺陷（§1–§5 已修复）。

**示例（真实工程，仅作证据、不作通用规则）**：

- `netfind PD1` → `U300.PD1 + R307.1`（2 个点），**不含 `+3V3D`**；
- `+3V3D` 是另一条 57 点网络；
- 链路：`PD1 → R307 → LED1.+#3`，`LED1.-#1/#4 → GND`；
- 结论：MCU 驱动 LED，不是电源指示——`netfind` 的判断正确，没有漏查。

给结论时的判据：

| 问题 | 该用什么 | 说明 |
| --- | --- | --- |
| 这个网络上有没有某电源/某器件 | `netfind` | 充分；返回整组别名成员 |
| 这个引脚经串阻/二极管连到哪 | `pinmap` 逐脚 / `trace` | `netfind` 不跨器件 |
| 这颗器件在哪个板/页、连了哪些网络 | `find` | 含别名分组与跨页 |
| 二极管方向、两端网络 | `polar` | 只陈列事实，不做电气裁决 |
