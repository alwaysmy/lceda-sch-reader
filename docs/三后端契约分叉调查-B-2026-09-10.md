# 三后端契约分叉（B 项）调查报告 · 2026-09-10

> 背景：`lceda_reader.py` 用三个后端（LcedaDB=.eprj2 V2 SQLite、
> EproDB=.epro V2 ZIP、Epro2DB=.epro2 V3 ZIP/解密）实现同一
> duck-typing 接口，命令层复用。AGENTS 原则要求"格式差异只在后端内
> 归一化，新消费点禁止自行解析原始 segs/坐标"（`docs/开发文档.md` §2）。
> 本报告盘点当前哪些差异**已正确收进后端**、哪些**泄漏到共享层**或
> **三后端不一致**，评估风险与修法。**B 是三后端里最大的改动，
> 动连通域地基，必须逐项探针 + 全量回归，先汇报再动。**

## 一、接口层设计（现状）

`SchemaBackend` ABC 声明：`schematics/schem_map/sheets/sheet_text/
sheet_records/device_map/device_attrs/symbol_of_device/symbol_pins/
datasheet_rows/hierarchy`。可选：`decompress/symbol_records/
cbb_symbol_board_map/pcb_docs/pcb_inventory/doc_metas`。

## 二、已识别差异（按风险排序）

### B1. 坐标原点（origin）处理三后端不一致【潜在高】

- `LcedaDB.symbol_pins`（`lceda_reader.py:577`）：引脚坐标**不**减
  origin（直接 `a[4]/a[5]`）。
- `EproDB.symbol_pins`（`:929`）：减 `HEAD.originX/originY`
  （`:961-962, 970-971`）。
- `Epro2DB.symbol_pins`（`:1540`）：减 `CANVAS.originX/originY`
  **并 Y 取反**（`:1580-1581, 1602-1603`）。
- 基类 `symbol_records` 文档（`:216-221`）却写"origin 偏移由渲染器
  统一处理"——与 EproDB/Epro2DB 在 `symbol_pins` 内减 origin 矛盾。
- **实测**：涡流.eprj2（Lceda）116 个符号 origin 全为 0；
  Piezo.epro（Epro）193 个符号中 6 个 origin 非零（含 symbolType=2
  普通器件，如 `0f438996d0ff` (-30,30)、`eea432e02251` (0,40)）。
  故 Lceda 不减、Epro 减 **在当前样本下结果一致**（Lceda origin 恒 0），
  但这是"碰巧"，非契约保证。
- **风险**：若某 .eprj2 符号 origin 非零，LcedaDB 与 EproDB 引脚坐标
  口径将不同 → 连通域/渲染错位。**未全盘验证**。
- **修法**：统一为"`symbol_pins` 返回实例相对坐标（已减 origin）"，
  LcedaDB 也减（其 origin 取 HEAD；实测 0 则无行为变化）。
  并在接口文档写清坐标口径。

### B2. `COMPONENT a[2]` 语义三后端不同【中】

- `LcedaDB.sheet_records`（`:451`）：保留 a[2] 原值（V2 标题字符串）。
- `EproDB.sheet_records`（`:733`）：**强制 `a[2]=""`**（.epro 的 a[2]
  是符号 uuid 引用，非标题）。
- `Epro2DB.sheet_records`（`:1287`）：a[2] 放 `partId`（符号内 PART 名）。
- 共享层 `parse_sheet` 靠"title 为空时取 Name 属性兜底"（`:1982-1983`）
  容忍三者差异。
- **风险**：新消费点若假设 a[2] 是标题，在 .epro 上会拿到空串。

### B3. `_norm_segs` 格式差异泄漏到共享层【中】

- `_norm_segs`（`:1844`，模块级）同时处理 V2 嵌套段
  `[[x1,y1,x2,y2],...]` 与 .epro 平铺点链 `[x1,y1,x2,y2,...]`。
- 即"走线段表示差异"没有只收进后端，而是在共享层做兼容——
  与 AGENTS 原则 2 相悖。
- **修法**：把 segs 归一化移进各后端 `sheet_records` 输出（统一为
  嵌套段），共享层只按一种形状消费。

### B4. OffPage(docType=25) 映射仅 Epro2DB 有【低】

- `Epro2DB.symbol_pins`（`:1569-1570`）：25→19（按 NetPort 语义）。
- LcedaDB/EproDB 若有 docType 25 则透传（当前无样本）。
- `docs/开发文档.md` §4.3 标注为"推断，样例 0 实例"。

### B5. `symbol_records` 可用性【已知待办】

- LcedaDB/EproDB：返回原始图形原语（POLY/RECT/…）。
- Epro2DB：返回 None → 渲染退化为 bbox+引脚桩（V3 符号图形转换未做，
  见 `TODO.md`）。

### B6. CBB 原生映射【中】

- `EproDB.cbb_symbol_board_map`（`:843`）/`Epro2DB`（`:1682`）：有。
- LcedaDB：无 → `_expand_cbb` 回退"同目录 .eprj2 blockSymbols >
  端口集匹配"（不可复现，见 G 项）。

### B7. `symbol_of_device` 桥接差异【低】

- Device→Symbol 桥各后端机制不同（attributes 表 / symbols 映射 /
  META）；无桥接的后端返回 None，`symbol_of` 有兜底。

## 三、结论与风险

- **当前无已证实的线上 bug**：交叉验证（涡流 eprj2↔epro2、Piezo
  epro↔epro2）未暴露坐标错误；B1 的分歧在现有样本下因 origin=0 而
  恰好一致。
- **但契约不清晰**：origin 归属（后端 vs 渲染器）、a[2] 语义、
  segs 形状、OffPage 映射，都靠"共享层兜底"和"实测碰巧"维持。
- **风险点**：任何新消费点（新命令/新渲染路径）若不了解这些差异，
  容易在某一后端上出错，且不易察觉。

## 四、建议修法（待批准，不先行）

按"差异收进后端 + 契约文档化 + 回归护栏"三步：

1. **P1 坐标口径统一（B1）**：写跨后端坐标一致性探针——同一设计
   多格式（涡流 eprj2↔epro2、Piezo epro↔epro2）逐符号比对
   `symbol_pins`；据此统一 `symbol_pins` 口径（含 LcedaDB 减 origin）。
   **需先有非零 origin 的 .eprj2 样本**才能真验证（当前无）。
2. **P2 `_norm_segs` 下沉（B3）**：各后端 `sheet_records` 输出统一为
   嵌套段；共享层删除跨格式分支。回归：全 6 工程 netlist/pins 逐字节。
3. **P3 契约文档化（B2/B4/B5/B6/B7）**：在 `SchemaBackend` docstring
   或 `docs/开发文档.md` §2 明确每后端 a[2]/坐标/OffPage/映射语义，
   禁止消费点绕过 `sheet_records/symbol_pins`。
4. **护栏**：扩充 `probes/cross_backend_contract.py`，加"同设计多格式
   pinmap/netlist 一致性"断言。

**执行风险**：B1/B3 改动触及连通域地基（pinmap/netlist/trace 全链），
必须改前存全量基线、改后逐字节对比 + 全盘格式验证。按 AGENTS 纪律，
每步独立 commit 并附验证结论。
