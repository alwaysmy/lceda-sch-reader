# CBB 母图位号映射调查（加密 .eprj2 2 段 INSTANCE 格式）

2026-09-09。调查加密 `.eprj2`（新版分支格式）的 CBB 复用块母图位号
能否从文件读取。**结论：数据在文件里，格式已定位，实例关联键待解。**

> 起因：发现加密 `.eprj2` 的 CBB 展开用模板位号（`CBB6.U13`），
> 而官方 `.epro2` 用母图位号（`CBB6.U2`）。曾误判为"文件里没有母图
> 位号"，被用户质疑（EDA 能正确打开并显示母图位号，数据必在），
> 深挖后推翻该错误结论。

## 1. 已确认的事实

### 1.1 两种格式的 INSTANCE 文档 uuid 不同

| 格式 | INSTANCE uuid 形态 | 段数 | `cbb_instances()` |
| --- | --- | --- | --- |
| 加密 .eprj2 | `<schematic_uuid>_$<page_uuid>` | 2 | 0（被跳过） |
| .epro2（官方导出） | `<sch>_$<page>~<inst_cid>_$<template_page>` | 3（含 `~`） | 65 |

样例：
- 加密 .eprj2：`120095be3ade3af5_$bc4b7a6e175284e5`
- .epro2：`0298ad21004bd80d_$58759deb39a23a10~b65b77a4bd3a9209_$91f2f32dd87f93f8`

`lceda_reader.py` 的 `Epro2DB.cbb_instances()` 要求
`len(parts) >= 3 and "~" in parts[1]`，故 2 段格式被整段跳过。
`Piezo_Driver_offline.epro2` 与加密 .eprj2 同为 2 段、`cbb_instances()=0`。

### 1.2 母图位号确实在加密 .eprj2 的 history_data 里

解密后 `INSTANCE_ATTR` 记录含 `Designator`（母图位号）：
```
{"type":"INSTANCE_ATTR","ticket":2433,"id":"e2"}||{"Unique ID":"gge260_4","Designator":"U27"}
{"type":"INSTANCE_ATTR","ticket":2433,"id":"e4"}||{"Unique ID":"gge261_4","Designator":"C133"}
```
- `id`（e2/e4/e12…）= **模板页元件 cid**（模板 `_CBB_MAX5318_2L::P1`：
  e2=U13、e4=C40、e12=C41…）
- `Designator` = **母图位号**（U27/C133/U26/C89…）
- 同一 2 段 uuid 下多个 ticket 段（2432/2434/2436/2438，各 22 条）。

### 1.3 与官方 .epro2 数据完全一致（决定性验证）

加密 .eprj2 `ticket=2432` 的 22 个母图位号集合，与 epro2
`cbb_instances()[(page=a43d16b468609165, cid=b65b77a4bd3a9209)]` 的
`members.values()` **差集为 0**（`ticket=2434` 同理匹配另一个实例）。
即两格式表达的是同一份母图映射。

### 1.4 结构表与实例节点不含此数据

- `projects.block_symbol_attrs_groups` = 空 `{}`。
- `project_structures.blockSymbols` 仅"符号 uuid→模板板名"（`source`
  为外部 CBB 库引用），无实例级成员映射。
- CBB 实例文档属性仅 `Symbol`/`Designator`/`NO_CONNECT`/`Relevance`。
- 模板位号（C40/U13）只在模板页元件属性。

## 2. CDP 活模型证据（ground truth）

`SCH.gVars.projectMgr.instanceAttrMgr.savedData` 只有 3 条，key 即 3 个
2 段 uuid，内容与文件 INSTANCE_ATTR 一致：
- `4f249e11..._$8a386fe3`（IsoInterface 页 sch_1）22 条，无 Designator
- `0298ad21..._$822c474a`（IsoInterface 页 sch_2）22 条，无 Designator
- `120095be..._$bc4b7a6e`（IsoInterface 页 sch）88 条：
  短 cid（e2/e4…）带 Designator + 长 cid（35a8d666…）仅 Unique ID 混排

`instanceAttrMgr` 原型方法：`get/getByPrefix/getWithInstanceDevice/
hasInstanceAttr/filter/...`；`getByPrefix('120095be3ade3af5')` 返回 0。

**CBB 实例（ControlDAC 页 e14754）活模型 children 仅 25 个**
（矩形+引脚），**不含展开的成员元件**——EDA 展开 CBB 是渲染/按需进行，
不在实例节点上存成员。

## 3. 未解点（下一步）

**INSTANCE 文档挂在 IsoInterface 页，但 CBB 实例在 ControlDAC 页**
（页 uuid 不同）。2 段 uuid 无 inst_cid，如何把某 ticket 段关联到具体
CBB 实例（如 CBB6 cid=e14754）尚未解码。

候选线索：
1. `ticket` 序列（2432/2434/2436/2438）与实例序号的对应；
2. Unique ID 的 `_N` 后缀（`gge260_4` 的 `_4`）可能与实例序号有关；
3. 页间引用关系（IsoInterface 页可能记录了它引用的 CBB 实例）。

**严禁记为"无法拿到"**——数据已确认在文件内，只是关联键待解。

## 3b. 2026-09-10 深入：EDA 源码 + 活模型 + DB 表（关键）

### 3b.1 EDA 源码消费方式（sch.js）

`assets/pro-sch/3.2.173.../js/sch.js` 中，渲染元素时读实例属性：
`SCH.gVars.projectMgr.instanceAttrMgr.getWithInstanceDevice(<pageUuid>)
.attr[<elementCid>]`。即 EDA 侧实例属性**按页 uuid 取**，键为元素 cid
（模板 cid）。`instanceAttrMgr` 的 `savedData/unsavedData` 键为
`<schematic>_$<page>`。

### 3b.2 活模型实测（ground truth）

- `instanceAttrMgr.savedData` 仅 3 条，键均为
  `<schematic>_$<IsoInterface页>`（`bc4b7a6e` 等）。
- `get('<schematic>_$<IsoInterface页>')` 返回 44 条 attr（含 e2→U26 等），
  但**不含 U27**——U27 那组（ticket 2432）被同 (type,id) 的更高 ticket
  段覆盖（增量合并后只剩最后快照）。
- 对 CBB 实例页（`a43d16b4` ControlDAC_B）的多种键调用
  `get/getWithInstanceDevice`（页 uuid / CBB cid e107 / 符号 uuid /
  `sch_$page` 组合）**均返回空或不含成员位号**。
- 装 hook 监控 `get/getWithInstanceDevice`，切换/重开 CBB 页**未捕获
  任何调用** → CBB 成员位号的渲染**不走** `instanceAttrMgr`。
- IsoInterface 页（`bc4b7a6e`）**无 block_symbol 节点、无 CBB 模板符号**
  （131 元件全为普通器件/端口/短接符）；ControlDAC_B 确有 block_symbol
  `e107/e108`（sym=1cc4f0d4，MAX5318 模板），但其 `_attrMap` 为空。

### 3b.3 DB 表：CBB 成员属性的正确 store 为空

本地库存在专用表 `block_symbol_attributes`（列 `path, project_uuid,
hash, ticket, attr`）——正是承载"实例 path → 成员属性"的结构；实测
**0 行**。`projects.block_symbol_attrs_groups` 亦为空 `{}`。

### 3b.4 EDA 源码解析（sch.js 反查）

- 分隔符 `lc = "_"`；判定函数 `Pt(i) = (i.split("_").length > 2)`——
  **3 段（epro2 格式）为 true，2 段（加密 eprj2 格式）为 false**。
- 3 段路径含 `~`（`dce="~"`），形如
  `<sch>_$<page>~<instCid>_$<template>`；`E6()` 对两种格式分别解析为
  标题（2 段那支只解出 board/sheet 标题做显示，**不含实例成员映射**）。
- **`getByPrefix(e)`**（CBB 成员读取入口）实现：
  `Object.keys(savedData).filter(r => Pt(r) && Hue(r,e))`——
  **只认 3 段（Pt=true）路径**。本项目 savedData **无任何 3 段键** →
  `getByPrefix` 恒返回空。
- **写入接口** `setByPropertyKey(path, elementCid, key, value)` →
  `setByPage(path, ...)`，键即**实例路径（3 段）**。本地库无该键。
- refdes 分配用 `part.attrs["Reuse Block"]` + `Group ID`（`I6()`）；
  实测本项目 CBB 实例的 `Reuse Block`/`Group ID` **全为空/None**。
- `getWithInstanceDevice(<页面路径>).attr[<元素cid>]` 的消费点属
  搜索/查换等功能；hook 监控显示 **CBB 页渲染不调用它**。

### 3b.5 结论（**已暂时搁置**，2026-09-10）

> **重要更正（用户指出）**：既然导出 `.epro2` 能产生完整实例级映射，
> 说明**导出时信息在**（信息未损失才可能导出）。故**不能推断"本地库
> 不含该信息"**。本轮的"孤儿数据"观察只能说明：**我们在 history_data 里
> 找到的页面键（2 段）INSTANCE 文档不是导出所用的那个映射源**——我看错
> 了来源，而非数据缺失。

- 已确认事实（保留）：
  - 母图位号存在于文件（页面键 INSTANCE_ATTR，与 epro2 数据一致）。
  - EDA 源码：`getByPrefix` 只认 3 段（`Pt`）路径；`setByPropertyKey`
    以 3 段实例路径为键。
  - 本轮观察到的 2 段页键条目，其 attr id（e2/e4）在挂载页上不存在
    → 说明**它是另一套语义**（或另一版本快照），不是 CBB 实例映射源。
- **未查明**：本地加密 `.eprj2` 中承载实例级映射的真实来源（导出链曾在
  内存/加载态拥有它）。**本项标记为"暂时搁置"**，不再投入本轮；恢复调查
  时优先查 EDA 加载/导出时如何**重建**该映射（内存结构、`pureSchematics`、
  或 `block_symbol_attributes` 的写入时机）。
- 现状处理：加密 .eprj2 展开 CBB 用模板位号（正确但不含母图改名的精确
  位号）；**需要精确母图位号时用 `.epro2`**（导出或 `export_newfmt.py`）。

### 3b.6 恢复调查时的候选（搁置）

1. EDA 加载工程时如何从模板 + 实例信息**重建**成员映射（导出链的输入）。
2. CDP 对某 CBB 成员改名并保存，观察本地库**写入位置**（哪张表/哪个键）
   ——正向确认真实存储，而非逆推。
3. `.epro2` 导出脚本（`export_newfmt.py`）当前抓 `instanceAttrMgr`
   `savedData/unsavedData`；核对导出时它拿到的键形态（可能导出前的内存
   态与磁盘不同）。

## 4. 影响与临时方案

- 加密 `.eprj2` CBB 展开当前回退模板位号（`CBB6.U13`）；
  `.epro/.epro2` 用母图位号（`CBB6.U2`）。两种口径均"正确"但不同。
- 临时方案（未实施）：加密 .eprj2 展开 CBB 时 stderr 提示
  "本格式展开用模板位号（导出 .epro2 可获母图位号）"。
