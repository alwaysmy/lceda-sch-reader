# 格式兼容与设计模型方向（第一性原理复盘）

> 2026-08-31。本文纠正此前「审查工具是目的、openlceda 是范围蔓延」的误判，
> 并据此重新推导架构方向。配套文档：`docs/缺失分析与改进建议-2026-08-31.md`
> （具体缺失清单）、`docs/审查工具设计启发.md`、`docs/工程文件字段字典.md`。

## 一、前提（纠正）

- **openlceda 是终点，审查工具是为 openlceda 的格式兼容做准备。**
- 读厂商格式（.eprj2/.epro/.epro2/新版加密）**不是风险，是主线**——
  不读厂商格式就没有审查工具，也就没有格式兼容可言。
- 因此「绑定厂商私有格式 = 战略脆弱」这条不成立：**跟踪厂商格式正是目标本身**。

## 二、核心结论

核心资产是「**格式知识 + 一个无损的归一化设计模型**」，不是审查规则。

审查的真正作用是**逼你把格式读懂、读全、读对**：要审一个设计，就得把
netlist、引脚、层级、PCB、值、文本、几何全部解析出来；解析错了会产生冤案，
所以审查天然是格式理解的强校验器。审查规则只是这个过程的副产品。

## 三、四个推论

### 1. 读的「完整性」优先于审查的「花样」

`TODO.md` 里的 BUS、V3 符号图形、PAD 几何、INSTANCE OVERRIDE，不能按
「能不能让审查更准」排优先级，而要按「会不会卡住完整格式理解」排——
它们是 openlceda 的格式缺口，不只是审查缺口，应**提前**。

反之，datasheet 核对、审查规则引擎、LLM 编排这些审查工具自身的增值，
对格式兼容这条主线应**靠后**。

### 2. 归一化模型要「无损」，不能只留「审查子集」

该模型将来要给 openlceda 的**写回**用，必须装得下格式里的全部内容：
LINESTYLE、锁定位、PART 定义、原始坐标、审查根本不在乎的字段等。否则无法
round-trip 回文件。因此模型的定义是「**格式的归一化**」，不是「审查视图」。

`docs/工程文件字段字典.md` + `reference/` 官方规范，就是这份无损模型的种子。

### 3. 读只是第一步，真正验收是 round-trip

round-trip = 读 → 模型 → 写回 = 不变。审查工具只能验「读对」，验不了
「写回对」，但**设计模型时现在就要按「将来能写回」去定义**，不要等写回那
一步再返工。ticket 合并、分支版本化这些写回难点，正是模型必须保留足够信息
才能面对的。

### 4. schema 是这个模型的「接口钉」

schema = 数据结构长什么样的书面契约（哪些字段、什么类型、哪些必有、如何
嵌套），并带版本号。审查规则、渲染、diff、LLM、以及未来的 openlceda 编辑器
都吃同一份模型，靠一份带版本的 schema 把它们钉在同一套结构上——这是现在
就能做、且顺着主线的一件事。

例（`pinmap --json` 的元件）：`designator` 字符串、`symbol_type` 整数、
`pins` 数组，其中每项含 `pin`/`name`/`net`/`net_inferred`/`peers`/
`wire_peers` 等——schema 就是把这些写下来并版本化。

## 四、收敛

先定义**无损、带 schema 版本的归一化设计模型**（以字段字典与官方规范为源），
让审查命令、渲染、diff 都改成消费它；审查规则与 datasheet 那些往后放，
因为它们不服务于格式兼容这条主线。
