# eprj3 与 V4 格式调研（2026-10-01）

调研"立创EDA 出 eprj3 / AI 原生支持"的实际情况，评估对 lceda_reader 的影响。

## 一、官方的"AI 原生"是什么

**`easyeda/easyeda-format-skill`**（MIT，v1.3.0，2026-09-22）——官方发布的
**面向 AI Agent（Claude Code）的格式生成技能**：

- 目标：让 AI 按类型定义与 JSON Schema **直接生成符合 EasyEDA Pro 格式的
  原理图/PCB/符号/封装/面板/仿真数据**，并用内置 `validate.js`（ajv）
  **强制校验**（`valid:true` 才允许返回）。
- 规模：15 个文档域、186 个图元、186 个示例、136 个 JSON Schema、类型索引
  `types-index.md`；渐进式加载（类型索引→文档层→图元层→示例/Schema）。
- 行格式与 V3 同构：`{type,id,ticket}||{data}|`（`|`+LF 收尾）；
  `validate.js` 支持 `<DOCTYPE>_<PRIMITIVE>` 前缀名或 `--doc`。
- 安装：clone 到 `~/.claude/skills/`（Claude Code 技能目录）。

> 上代文档仓库 `easyeda/easyeda-file-format`（V3 规范）README 已明示：
> 最新格式说明请看 `easyeda-format-skill`。

## 二、V4 与 V3 的差异（官方 FORMATLOG.md 摘要，10 条）

1. **总体架构不变**（日志式增量 + `||` 分层 + 行尾 `|`）。
2. **判优规则修正（重要）**：判优键 = **「文档 + 归一化 id」（`type` 不参与
   比较）**；`ticket` 大者胜；**平票时 DOCHEAD `client` 字典序大者胜**——
   老 V3/2.0 文档写"client 小者保留"，**与实现相反**，不可照抄。
3. DOCHEAD 增加 `updateTime`/`version`；`client`/`uuid` 限 16 位小写 hex；
   新增 **EDIT_HEAD**（最后编辑者）。
4. **docType 11→20**：`PROJECT_CONFIG`→`CONFIG`；新增 `EDIT_HEAD`、
   `PANEL_LIB`、`FONT`、`VARIANT`、`COMPONENT_GROUP(_DATA)`、
   `SIMULATION`、`SIMULATION_SCH`。
5. CANVAS：V4 固定 `id:"CANVAS"`、`ticket:1`；PCB unit 仅接受小写
   `mm`/`mil`（大写整行被丢弃）。
6. **坐标单位**：V3 全局 0.01 inch；**V4 的 PCB 改为 mil**（网格尺寸 ×10/÷10），
   原理图仍 0.01 inch 量级。
7. **`yAxisDirection`（eprj3 本地格式新增）**：`up`/`down`；本地文件固定
   **Y 轴向上**写出，附逐字段翻转对照表（`rotation`/`isMirror`/`zIndex`
   及幅值字段不翻转）。
8. 布尔统一 `true/false`（V3 规范写 1/0）；颜色：`null`=主题默认，
   PCB/面板支持 `rgb()`/`cmyk()`/`data:`/`blob:`。
9. **删除语义细化**：`META` **绝不可**用空串删除（消费方取 `dataObj.title`，
   空串→null 抛异常中止整批重放；删 META 走 `DELETE_DOC`）；
   `DELETE_DOC` 载荷必须是 `{"isDelete":true|false}`（发空串会被判"未删除"
   而复活文档）；`INSTANCE_ATTR` 空串=删除该属性（正确载荷）。
10. 图元差异：PCB `ARC`/`CARC` 统一为 `ARC`+`arcType`；新增
    `X_NET`/`X_NET_GROUP`、`D3_ATTRIBUTE`；V3 的 `ITEM_ORDER`/`CONNECT`/
    `PROP`/`REUSE_BLOCK` 在 V4 枚举中不见；新增控制原子 `META_SORT`/
    `META_Z_INDEX`/`VARIANT_GROUPED`/`GROUP_INDEX`/`GROUP_DATA`/
    `ELE_PLACEHOLDER`/`META_PLACEHOLDER`。

## 三、.eprj3 是什么

**文件夹式**工程格式（非单文件 SQLite）——面向 Git 与 AI 工具：

```
MyProject/
├── MyProject.eprj3        # 工程索引/元数据（唯一初始文件）
├── sch/<板名>/<页名>.esch2 # 原理图页源码（JSON 记录行）
│            <板名>.ecfg    # 设计规则
│            <板名>.evar    # 装配变体
├── pcb/<板名>.epcb2        # PCB 源码
└── panel/<名>.epan2        # 面板源码
```

- 记录仍是 `type` 驱动的 JSON 行（DOCHEAD/META/COMPONENT/ATTR/WIRE/
  NETLABEL/PORT/TEXT/OBJ…），与 V3/V4 日志同构。
- 名称取自文件名/文件夹名；无独立工程库（器件/符号/封装为工程内独立文件）；
  图片与字体随文档走；不存缩略图与预览树。
- 本仓库 `reference/eprj3-format.md` 已有该说明（引官方仓库与
  prodocs.easyeda.com/lceda.cn）。

## 四、对 lceda_reader 的影响

- **现状**：reader 支持 `.eprj2`(V2.2 SQLite/加密) / `.epro`(V2 ZIP) /
  `.epro2`(V3 ZIP 增量)。**尚不支持 `.eprj3`（V4 文件夹）**。
- **本机客户端 3.2.175**：资源内**无 `eprj3` 字样**；`esch2` 仅出现在
  chameleon 转换模块（3.2.40）。本机也**无 `.eprj3` 工程**——推断该格式
  支持在更新版客户端（社区可见 3.2.186）或需显式启用。
- **可行性**：新增 `Eprj3DB` 后端相对可行——文件夹 + 同样 `{type,id,ticket}`
  行记录；差异需处理：docType 扩充、**PCB mil 单位**、`yAxisDirection`
  翻转表、布尔/颜色编码、新原子类型、`CONFIG` 改名。
- **判优规则核对（本次实测评估）**：我们 `Epro2DB._iter_doc_lines` 用
  `key=(type,id)` + `rank=(段序,ticket)`；官方 V4 为「文档+归一化 id」
  （type 不参与）+ 平票比 client。实测 28 个 `.epro2`：
  **跨 type 同 id = 0**；同 (doc,id,ticket) 平票 25 处（全在
  `Piezo_Driver_offline.epro2`，**全部为 FONT 原子且 body 完全一致**，
  分布在不同段的多个 client）→ **行为等价，无需改**。
  记录为待验证项：若未来出现"平票 + body 不同"，需按 client 大者胜实现。
